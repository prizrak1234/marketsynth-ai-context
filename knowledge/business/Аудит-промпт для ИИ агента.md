## Шаг 2 — Оцени по 12 критериям

Оцени каждый критерий от 1 до 10. Для каждого дай:
- Оценку (1-10)
- 1-2 строки: что хорошо
- 1-2 строки: что не хватает или сделано слабо

### Критерий 1: Идентичность агента
Понятно ли кто этот агент, для кого он работает и как его зовут?
Есть ли имя, роль, контекст запуска (Telegram / терминал / API)?

### Критерий 2: Профиль владельца
Знает ли агент кто его использует?
Есть ли: имя, стек, язык общения, главный критерий ("экономит время / увеличивает доход")?
Без этого агент работает "в пустоту" — отвечает универсально, а не под конкретного человека.

### Критерий 3: Правила коммуникации (анти-клише)
Есть ли явный список запрещённых фраз и поведений?
("Certainly", "Great question", нарратив процесса, избыточные извинения)
Конкретные запрещённые слова → выше оценка, чем общее "не болтай".

### Критерий 4: Маршрутизация задач и моделей
Есть ли правила выбора: какую модель / инструмент / субагента использовать для какого типа задачи?
Триггеры ("YouTube URL → youtube-analyzer", "большой файл → Gemini") оцениваются выше чем общие слова.

### Критерий 5: Верификация результата
Требует ли промпт физически проверять что работа выполнена?
("ls", "cat", "grep" после записи файла — не доверять на слово, что всё сохранилось)
Это предотвращает класс ошибок "сказал 'готово' но файл пустой".

### Критерий 6: Управление контекстом и памятью
Есть ли правила:
- когда делать /compact и при каком % контекста
- как писать в память (scope, замена устаревшего, краткость)
- политика истечения памяти (что хранить постоянно, что через 30 дней удалять)

### Критерий 7: Безопасность и автономность
Есть ли чёткое разграничение:
- что агент делает сам (автономно)
- за чем спрашивает подтверждения (approval gate)
Особенно: удаление файлов, изменение кода в src/, изменение .env
Лучший паттерн — Autonomy Matrix: таблица AUTONOMOUS vs CRITICAL.

### Критерий 8: SOP для повторяемых задач
Есть ли конкретные пошаговые алгоритмы для частых задач?
Не "помоги с контентом", а "шаг 1 → шаг 2 → шаг 3" с путями и форматами.
Каждый SOP в промпте = одна меньше объяснялка вручную.

### Критерий 9: Накопление опыта (Learned Patterns)
Есть ли механизм записи уроков из реальных сессий?
Learned Patterns, dream, changelog — то что заставляет промпт расти.
Статичный промпт = мёртвый промпт. Оцени 10/10 только если паттерны обновляются автоматически.

### Критерий 10: Поддерживаемость файла
Легко ли обновлять промпт не ломая остальное?
Разделены ли постоянные правила и временные workflow?
Нет ли дублирования и противоречий?
Есть ли правило на замену устаревшего вместо накопления?

### Критерий 11: Архитектурная декомпозиция (ВАЖНЕЙШИЙ)
Это самый часто упускаемый критерий.

Оцени: вынесено ли из основного файла то, что не нужно в каждой задаче?

Правильная архитектура:
  ядро (50-150 строк): кто агент, правила, routing, learned patterns
  ↓ делегирует
  субагенты: специализированные инструкции под конкретные задачи
  скиллы: повторяемые операции с предсказуемым вводом/выводом
  specs/: детальные workflow, которые агент читает только по триггеру
  hooks: автоматические действия (post-compact, pre-session)

Вопросы для оценки:
- Есть ли ссылки на субагентов / specs вместо дублирования деталей внутри?
- Загружает ли агент контекст лениво (только когда нужно) или жадно (всё всегда)?
- Если файл > 200 строк — проверь: каждый блок нужен в КАЖДОЙ задаче?

Признаки плохой декомпозиции:
- Все workflow в одном файле (YouTube + контент + код + Obsidian вместе)
- Детальные инструкции по сервисам прямо в ядре вместо specs/
- Нет ссылок на субагентов или скиллы
- Нет паттерна "trigger → read spec → execute"

Оценка: 1-4 = всё в одном файле | 5-7 = частичная декомпозиция | 8-10 = чистое ядро + делегирование

### Критерий 12: Инженерная защита (File Edit Policy)
Есть ли правила защиты от деструктивных действий с файлами?
- Читать файл полностью перед редактированием
- Использовать replace/patch, а не write/перезапись для существующих файлов
- Если replace не нашёл совпадение — остановиться и спросить
- Проверять после изменения что остальные разделы целы
Отсутствие этого правила → риск: агент переписывает файл целиком и теряет существующие настройки.

## Шаг 4 — Архитектурный разбор (отдельный блок)

Если файл > 150 строк, выполни дополнительный анализ:

### 4.1 Что вынести из ядра в specs/
Список блоков которые нужны только в конкретных задачах, а не всегда:
- [блок X] → specs/X.md (загружать по триггеру "...")
- [блок Y] → specs/Y.md (загружать по триггеру "...")

### 4.2 Что превратить в субагента
Задачи, для которых стоит создать отдельного специализированного агента:
- [задача X] → agents/X.md (запускать когда "...")

### 4.3 Что превратить в скилл
Повторяемые операции с предсказуемым вводом/выводом:
- [операция X] → skill X (триггер: "...")

### 4.4 Оценка потенциальной экономии контекста
Сейчас: агент читает N строк при каждом запуске
После рефакторинга: агент читает ~M строк + N строк субагента по запросу
Экономия: ~X% контекста на стандартных задачах

## Шаг 6 — Финальный вердикт

**НОВИЧОК (0-48/120):** Промпт работает, но агент без характера и архитектуры. Нужна переработка.

**РАБОЧИЙ (49-72/120):** Есть хорошие блоки, но агент непредсказуем и контекст тратится неэффективно.

**ПРОДВИНУТЫЙ (73-96/120):** Сильный промпт. Скорее всего перегружен — пора рефакторить в core + specs.

**PRODUCTION-READY (97-120/120):** Агент — надёжный сотрудник с чистой архитектурой. Только итерация.

## Важно при анализе

- Оценивай по операциональной полезности, а не по длине
- Короткий файл с делегированием > длинный файл со всем внутри
- Конкретные forbidden phrases > общее "не болтай"
- Пример команды с синтаксисом > описание что команда делает
- Реальные Learned Patterns из сессий > теоретические принципы
- Trigger → spec → execute > детальная инструкция прямо в ядре
- Файл должен расти на основе опыта, а не пухнуть от накопления

## Ключевые принципы из нашего исследования

### Главный принцип: CORE + ДЕЛЕГИРОВАНИЕ

```
Хороший агент = маленькое ядро (кто я + правила + routing + learned patterns)
              + субагенты (специализация под задачи)
              + скиллы (повторяемые операции)
              + hooks (автоматические триггеры)
```

**Правило эволюции промпта:**
1. Стартуешь с одним большим файлом — это нормально
2. После 2-3 месяцев работы — рефакторишь: что из файла нужно в каждой задаче, а что только иногда
3. "Иногда" → выносишь в specs/ или субагент
4. Оставшееся ядро должно быть 80-150 строк

---

### Что каждый агент делает лучше всех

| Агент | Главная сила | Применять когда |
|-------|-------------|-----------------|
| **ClaudeClaw** | Learned Patterns, знает владельца | Нужна память об ошибках и персонализация |
| **GeminiClaw** | Silent Execution + Autonomy Matrix + делегирование | Нужна строгая тихая работа + чистая архитектура |
| **CodexClaw** | Risk Profiles + Acceptance Criteria | Работа с кодом, деструктивные операции, чёткие критерии |

---

### Антипаттерны: что делать нельзя

❌ **Класть всё в одно ядро** — агент читает 400 строк при вопросе "напиши пост"
❌ **Дублировать файлы** — YL_AGENTS.md = AGENTS.md, оба устареют по-разному
❌ **Описывать стиль словами** — "будь кратким" vs список forbidden phrases
❌ **Статичный промпт** — без Learned Patterns файл не растёт из реального опыта
❌ **write_file для редактирования** — перезаписывает всё, теряет существующие правила

### Лучшие блоки для вдохновения

**Autonomy Matrix (из GEMINI.md):**
```markdown
AUTONOMOUS (делать без спроса):
  — ~/obsidian-vault/, workspace/
  — Обновление agents/ и skills/

CRITICAL (нужно одобрение):
  — src/, .env, package.json
  — Удаление файлов (кроме workspace/tmp/)
```

**Learned Patterns (из ClaudeClaw_CLAUDE.md):**
```markdown
## Learned Patterns
*Обновлено: YYYY-MM-DD (AutoDream, N сессий)*
• [что пошло не так] → [как исправили] → [результат в N следующих сессиях]
```

**Делегирование (из GEMINI.md):**
```markdown
## Delegation
@obsidian-librarian — для ЛЮБЫХ операций с vault
@content-writer     — для контентных задач
@youtube-analyzer   — автоматически при YouTube URL
```

**Risk Profiles (из AGENTS.md):**
```markdown
low:    небольшие правки → минимальный контроль
medium: несколько файлов → обязательная верификация
high:   production, удаление → second opinion
```

**Compact агрессивно (из ClaudeClaw_CLAUDE.md):**
```markdown
/compact при 40%, не при 60% — субагентные результаты
раздувают контекст. Кеш живёт 5 минут.
```

**File Edit Policy (из GEMINI.md):**
```markdown
ВСЕГДА читай файл перед правкой.
Используй replace/patch, НЕ перезапись.
Если replace не нашёл — стоп, спроси.
После правки: проверь grep что остальное цело.
```
