## Проблема: почему обычный RAG и обычные чаты не работают

### Проблема №1 — Stateless AI (ИИ без памяти)

Каждый раз когда ты начинаешь новый чат с GPT или Claude, он ничего не помнит из предыдущих сессий. Ты тратишь токены (и время) на восстановление контекста: "вот что мы делали, вот архитектура, вот наши решения..."

Это как иметь сотрудника с амнезией, который каждое утро не помнит ничего из вчерашнего дня.

### Проблема №2 — Классический RAG слишком сложный и "чёрный ящик"

RAG (Retrieval-Augmented Generation) — стандартный способ дать LLM доступ к личным данным:
1. Документы режутся на произвольные "чанки"
2. Чанки конвертируются в математические векторы (embeddings)
3. Хранятся в специальной векторной базе данных (Pinecone, Chroma и т.д.)
4. При вопросе система ищет похожие векторы и подаёт их в LLM

**Проблемы RAG:**
- Нужна векторная БД — инфраструктура, деньги, сложность
- "Черный ящик" — непонятно почему нашёлся именно этот чанк
- Трудно проверить и аудировать
- Статичный — нужно переиндексировать при изменениях
- Плохо работает на связях между концептами
- Избыточен для личных/персональных баз знаний

### Проблема №3 — "Забытые закладки" и рассеянное знание

Исследователь читает 50 статей, сохраняет в Pocket/Notion, никогда к ним не возвращается. Информация есть, но она мёртвая. Никак не соединена, не синтезирована, не активирована.

## Решение Karpathy: LLM как компилятор знаний

Вместо RAG с векторными базами — **LLM, который сам является "библиотекарем"**: читает сырые данные и компилирует их в структурированную wiki из Markdown-файлов.

Аналогия с кодом:
```
raw/           →  исходный код (.c, .py файлы)
LLM compiler   →  компилятор (GCC, Python interpreter)
wiki/          →  исполняемый файл + документация
health checks  →  тест-сюита (unit tests)
queries        →  runtime (запуск программы)
```

**Obsidian** выступает как IDE — фронтенд для просмотра всей этой системы.

## Архитектура: 4 фазы

### Фаза 1: Ingest (Сбор сырых данных)

Всё складывается в папку `raw/`:
- Веб-статьи → через **Obsidian Web Clipper** конвертируются в `.md` + изображения скачиваются локально
- Научные статьи с arXiv
- GitHub репозитории
- Датасеты
- Скриншоты, PDF

Ключевой принцип: изображения хранятся локально, чтобы LLM мог обращаться к ним через vision-возможности.

### Фаза 2: Compile (LLM компилирует wiki)

LLM читает `raw/` и создаёт структурированную wiki в директории `wiki/`:
- **INDEX.md** — краткое описание всех документов (входная точка для любого запроса)
- **Концептуальные статьи** (~100 статей, ~400K слов) — по одной на каждый концепт
- **Бэклинки** — автоматически созданные связи между статьями `[[wikilinks]]`
- **Derived outputs** — слайды Marp, графики matplotlib, ответы на прошлые запросы

Karpathy: *"The LLM writes and maintains all of the data of the wiki. I rarely touch it directly."*

### Фаза 3: Query & Enhance (Запросы и обогащение)

- **Obsidian IDE** — просматривать wiki и визуализации
- **Q&A Agent** — сложные исследовательские вопросы по всем статьям
- **Search Engine** — вручную написанный поисковик по wiki (web UI + CLI для LLM)
- Критически важно: **все ответы и выводы сохраняются обратно в wiki** — каждый запрос добавляет ценность

### Фаза 4: Lint & Maintain (Обслуживание и "починка")

LLM регулярно проводит "health checks":
- Ищет противоречия между статьями
- Заполняет пробелы через веб-поиск
- Находит новые связи между концептами
- Предлагает темы для новых статей

После lint → снова Фаза 2. Цикл работает постоянно.

## Структура директорий

```
my-research/
├── raw/                    ← сырые источники (не трогать руками)
│   ├── article-1.md
│   ├── paper-2.md
│   └── images/
├── wiki/                   ← LLM-скомпилированная wiki
│   ├── INDEX.md            ← всегда читается первым
│   └── concepts/
│       ├── concept-a.md
│       └── concept-b.md
├── output/                 ← результаты запросов, слайды, графики
└── _meta/                  ← состояние компиляции, конфиги
```

## Ключевые принципы подхода

**1. Без векторной БД** — при личном масштабе (~100 статей) INDEX.md + контекстное окно LLM достаточны для поиска. "Fancy RAG" добавляет latency и "retrieval noise" там, где они не нужны.

**2. Всё в Markdown** — human-readable, LLM-friendly, Git-совместимый, не привязан к vendor'у, работает в любом редакторе. Если Obsidian исчезнет — файлы останутся.

**3. Знания накапливаются** — каждый запрос, каждый chart, каждый ответ складывается обратно в wiki. Система умнеет от использования.

**4. Прозрачность** — любой факт можно отследить до конкретного `.md` файла в `raw/`. Нет "чёрного ящика" векторных embeddings.

**5. File-over-app философия** — пользователь владеет данными. AI — это умный редактор, который "приходит в гости" к файлам, а не забирает данные в облако.

**6. LLM сам пишет wiki** — ты редко редактируешь wiki вручную. Это территория LLM.

## RAG vs Karpathy Markdown Wiki

| Критерий          | Vector DB / RAG                           | Karpathy Markdown Wiki                   |
| ----------------- | ----------------------------------------- | ---------------------------------------- |
| Формат данных     | Непрозрачные векторы (математика)         | Human-readable Markdown                  |
| Логика поиска     | Семантическое сходство (nearest neighbor) | Явные связи (бэклинки, индексы)          |
| Аудируемость      | Низкая (черный ящик)                      | Высокая (прямая трассировка)             |
| Накопление        | Статичное (нужно переиндексировать)       | Активное (само-лечение через lint)       |
| Идеальный масштаб | Миллионы документов                       | 100–10,000 высококачественных документов |
| Инфраструктура    | Нужна векторная БД                        | Просто папка с файлами                   |

Аналогия: RAG = огромный неорганизованный склад с быстрым погрузчиком. Markdown Wiki = кураторская библиотека с главным библиотекарем, который постоянно пишет новые книги, объясняющие старые.

## Будущее: Synthetic Data и Fine-tuning

Karpathy намекает на следующий шаг:

Когда wiki достаточно выросла и "очищена" через linting → она становится идеальным обучающим датасетом. LLM можно **дообучить** на wiki. Тогда модель "знает" личную базу знаний в своих весах — не только через контекстное окно. Персональная исследовательская база → кастомная частная модель интеллекта.

## Как начать (минимальный сетап)

**Шаг 1.** Установи Obsidian (бесплатно, локальный) + расширение Obsidian Web Clipper

**Шаг 2.** Создай структуру:
```
my-topic/
├── raw/
└── wiki/
    └── INDEX.md
```

**Шаг 3.** Начни клипать. Любая статья → Web Clipper → `raw/article-name.md`

**Шаг 4.** Дай Claude/GPT промпт компилятора:
```
Ты — компилятор wiki. Прочитай все файлы в raw/ и скомпилируй их в wiki/:
1. Определи ключевые концепты из всех документов
2. Создай по одной .md статье на концепт в wiki/concepts/
3. Каждая статья: что raw/ говорит об этом концепте
4. Используй [[wikilinks]] для связей между концептами
5. Обнови wiki/INDEX.md с оглавлением
6. Обрабатывай только файлы изменённые с последней компиляции
```

**Шаг 5.** Задавай вопросы по wiki. Всё интересное — сохраняй обратно в wiki.

**Шаг 6.** Раз в неделю — health check: "Найди противоречия, пропущенные связи, темы для новых статей."

## Наша реализация: ClaudeClaw + Obsidian

> Добавлено: 2026-04-07 — что мы построили на основе идей Karpathy и чем наш подход отличается

Karpathy признал: его система — "hacky collection of scripts". Мы построили то же самое, но как полноценную производственную систему с мультиагентной архитектурой.

### Что реализовали

**`scripts/wiki-compile.js`** — LLM-компилятор знаний:
```bash
node scripts/wiki-compile.js --topic "AI агенты"   # скомпилировать тему
node scripts/wiki-compile.js --scan                # авто-определить топ-5 тем из vault
node scripts/wiki-compile.js --all                 # пересобрать все страницы
```
- Ищет заметки по теме через grep по всему vault
- Читает до ~20K токенов из найденных файлов
- Claude синтезирует wiki-страницу с `[[wikilinks]]` и структурированными разделами
- Fallback на Gemini если Claude недоступен
- Обновляет `Wiki/INDEX.md` автоматически

**`scripts/wiki-audit.js`** — health check vault:
```bash
node scripts/wiki-audit.js         # полный аудит
node scripts/wiki-audit.js --fix   # аудит + запустить компиляцию
```
- Показывает % заметок со связями по каждой папке (bar chart в терминале)
- Находит изолированные заметки — кандидаты для компиляции
- Считает health score vault (сейчас 79% из 1558 заметок)

**`~/obsidian-vault/Wiki/`** — наш аналог `wiki/` у Karpathy:
- `INDEX.md` — автообновляемое оглавление всех страниц
- Каждое воскресенье 10:00 — авто-запуск `--scan` через планировщик

### Наша архитектура vs Karpathy

| | Karpathy | Наша реализация |
|--|----------|----------------|
| **Ingest** | Ручной Web Clipper | Авто: YouTube/TikTok/Instagram агенты пишут в vault |
| **raw/ эквивалент** | Начинает с нуля | 1558 заметок уже накоплено |
| **Компилятор** | "Hacky scripts" | `wiki-compile.js` — production Node.js |
| **Health check** | Ручной запрос к LLM | `wiki-audit.js` — метрики, score, кандидаты |
| **Модели** | Один LLM | Multi-model: Claude (синтез) + Gemini (сканирование) |
| **Расписание** | Нет | Каждое воскресенье — авто-компиляция |
| **Организация vault** | Вручную | Librarian-агент — выделенная роль |
| **Интерфейс** | IDE + CLI | Telegram → ClaudeClaw → агенты |

### Ключевое отличие: мультиагентная архитектура

У Karpathy один человек делает всё: клипает, компилирует, делает запросы.

У нас разделение ролей:

```
ClaudeClaw (оркестратор)
├── youtube-analyzer    → пишет в YouTube/
├── tiktok-analyzer     → пишет в TikTok/
├── instagram-analyzer  → пишет в Instagram/
├── content-writer      → пишет в Threads/, Posts/
└── obsidian (librarian)
    ├── организует структуру vault
    ├── запускает wiki-compile.js --scan
    ├── запускает wiki-audit.js
    └── поддерживает MOC/
```

Каждый агент **пишет контент в свою папку**. Librarian **организует** — перемещает, структурирует, компилирует Wiki. Никто не лезет в чужую зону ответственности.

### Почему один vault лучше чем "два vault" (решение проблемы contamination)

Kepano (CEO Obsidian) предлагал держать личный vault и AI-vault раздельно, чтобы не смешивать человеческое и AI-контент.

Наш подход: **один vault, чёткая структура папок, роли агентов**.

Плюсы:
- Не нужно переключаться между vault'ами
- Человеческие и AI-заметки видны вместе — перекрёстные `[[ссылки]]` работают
- Frontmatter с тегами позволяет фильтровать по происхождению если нужно
- Librarian знает всю структуру и может связывать заметки из разных источников

Цена: нужна дисциплина — каждый агент работает по правилам (соглашения о папках, именах, frontmatter). Поэтому в system prompt каждого агента есть блок с правилами vault.

### Статус внедрения (обновлено 2026-04-07)

- ✅ **Инкрементальная компиляция** — реализовано. `Wiki/.compile-state.json` хранит mtime каждого источника. Повторный запуск пропускает темы без изменений. `--force` для принудительной пересборки.
- ✅ **Автобэклинки** — реализовано. `wiki-backlink.js` строит словарь из 570 концептов (Wiki/ + MOC/) и автоматически добавляет [[wikilinks]] в заметки. Применено к Research/: 19 файлов, ~230 новых связей.
- ✅ **Weekly digest** — каждое воскресенье 9:00 авто-дайджест за 7 дней → Research/YYYY-MM-DD-weekly-digest.md
- ✅ **Telegram pipeline** — каждую среду 10:00 backlinks + компиляция wiki по темам из Telegram/
- ✅ **Cross-wiki Q&A агент** — реализовано. `wiki-qa.js` ищет страницы в Wiki/, обходит [[wikilinks]] на глубину --depth, Claude синтезирует ответ из нескольких источников. `--save` сохраняет ответы в Wiki/QA/ (знания накапливаются).
- ✅ **Визуализации (Marp)** — реализовано. `wiki-marp.js` конвертирует wiki-страницы в Marp-презентации (markdown-слайды). Сохраняет в Wiki/Slides/. Открываются в Obsidian или экспортируются в PDF через marp-cli.
- ✅ **Fine-tuning dataset** — реализовано. `wiki-finetune.js` читает Wiki/, генерирует 5 Q&A пар на страницу, сохраняет JSONL в формате OpenAI fine-tuning. Следующий шаг — отправить в OpenAI/Anthropic fine-tuning API.
